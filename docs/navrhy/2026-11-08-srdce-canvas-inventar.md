7. Milestones/tasks/dependencies/readiness: Desktop frontier/work-overview/card-checklist, spec.steps and Heart milestone/milestone-decide/task/ticket-issue/ticket-answer/cancel. Readiness read adapters incomplete.
8. Sketch/drawing: drawing/file/wireframe-context; scene revision and sketch stale callback. Heart attachment upload is not scene editing; named scene adapter missing.
9. Layout vs session view: persisted positions/layout distinct from React viewport/selection/filter. No shared plan mutation for another session focus.

11. Handoff/resume: packet,assignment,lease,workspace,results,trace. Native gate exists; named Heart packet/claim/resume coverage incomplete.
12. Additional existing behavior: flow workflow/runs, page intent, human/agent libraries, site-admin/design-system, pipeline/rule-review. Individually enumerated below.

## M1 operation receipt implementation and recovery boundary

`POST /api/canvas-plan` and `POST /api/oporahub/graph-proposals` accept optional `operationId` (`[A-Za-z0-9_.:-]{1,160}`). Existing callers remain compatible. A receipt is scoped by project, workspace, operation kind and ID, bound to the trusted actor and SHA256 of the complete canonical request including original CAS values. Exact completed replay returns the original response before checking current digest; a changed payload or actor yields HTTP409 `operation_conflict`. `dryRun` neither creates nor consumes a receipt.

`database/schema/canvas_operation_schema.py` is additive, registered in `project_schema.py` including project copy/archive tables. No existing data is transformed. Rolling back application code leaves this unused table intact; do not drop it during rollback, since that would erase replay protection for operations already issued.

Graph proposal creation and its completed receipt share the native SQLite transaction. Canvas plan writes retain the existing SQL/file boundary: a durable pending receipt records the prepared refs, blocks, base graph digest and base state revision before writing. Native graph IDs, edge IDs, specs, text and desktop revision are read back before completion. A failure after pending creation returns no success and later retries receive HTTP409 `operation_incomplete`; this is a partial-write journal, **not** a proven crash-safe distributed transaction or automatic recovery facility.

Recovery is currently operator-assisted: inspect the original exact request (CLI journal), receipt prepared refs, native graph, spec/text revisions and Desktop state against the pre-operation snapshot. Only a verified complete write may be finalized with its actual response. Only proof that none of the operation's graph/document/state writes survived permits releasing the pending identity for a retry. Mixed or uncertain SQL/file state requires reconciliation first. There is no public reset/finalize endpoint in this slice; do not use a fresh operation ID to bypass an incomplete receipt. M2 must add explicit tested recovery rather than infer success from an unchanged graph digest (document-only writes can keep that digest).

`backend/canvas/test_operation_receipts.py` exercises exact replay with stale CAS, HTTP trusted-actor conflicts, changed payload, dryRun/validation no receipt, project/workspace/kind separation, native proposal rollback when receipt completion fails, acceptance readback, graph-change replay, and failures injected at after_write/save_graph/readback. Initial targeted gate: 16 passed across this file, `test_canvas_plan.py` and HTTP `test_opora_graph_routes.py`. Final gate after adding prepared pending metadata: 22 passed across receipt tests and `test_opora_graph_changes.py`; this is not the full backend suite. The existing route wrapper can append transient `rePinned` notifications outside the receipt; persisted operation IDs, refs, digest and revision are replayed, but this ancillary live-run notification is not a promised byte-identical replay.
`plan_with_repin` is also outside receipt completion: interruption after Canvas completion but before execution repinning can leave a stale execution excluded from the next clean-candidate set. Receipt replay does not repair that execution. This is a remaining recovery boundary, beyond differing notification metadata; M2 must reconcile repinning explicitly. M1 pending graph-proposal creation does not use this wrapper.
