Základ plátna společný všem prostředím: CanvasService (canvas_service.py: registry.sqlite se seznamem projektů, db_for(projekt) pro projects/<id>/project.sqlite, git sync, view a save grafu; graf Git pracovního prostoru leží v datech plátna `canvas/workspaces/<wid>/graph.json` přes workspace_graph.py, starý `opora-canvas.json` ve worktree se jen jednorázově převezme a cílové repo se nepíše), validace grafu (graph.py), hlavní složka projektu (project_folder.py) a jednorázová migrace staré canvas.sqlite (migrate_to_project_folders.py). Uzel smí vedle `sourceRef` / `size` nést i nepovinné `blockOffsets` (posun odtažených bočních bloků proti kartě, porty `action` / `rule` / `material` s konečnými `dx` / `dy`); jeho tvar hlídá `validate_block_offsets` a `save_graph` ho ukládá beze změny (test_graph_block_offsets.py).

Kontext karty z knihovny: `card.fetch` (`{files?, docs?}`, 1–20 relativních cest v repozitáři, u `docs` i `https://`) a `card.fill` (pole, která agent vyplní, z `CARD_FILL_FIELDS`) ověřuje `card_agent_context.py` volaný z `validate_card` v graph.py (test_card_agent_context.py, docs/zive-zobrazeni-a-knihovna.md §5). Existenci souborů hlídá lint katalogu ve frontendu, uložení jen tvar.
Oblast (`kind: "area"`) smí navíc nést nepovinné `color`, jednu ze šesti hodnot v `AREA_COLORS`, ať jde skupiny na plátně rozeznat od sebe (test_graph_area_color.py).

Oracle nad plátnem: `commit_pairs.py` spáruje rozsah (oblast, sektor, uzel) s commity kódu podle větve, úlohy, traileru nebo vlastněných cest; `sync_signals.py` z hotových dat spočítá echo a `sync_verdicts.py` z něj verdikt brány 1:1 (smí se commitnout, smí do mainu); `sync_report.py` jako jediný z nich sahá na disk a git a sbírá pro ně důkazy. Nic z toho nezapisuje. Kontrakt: `docs/synchronizace-pravdy.md`.
Jediná výjimka je `check_runs.py` (tabulka `check_runs`): append-only zápis hotového výsledku kontrol k jednomu commitu, ze kterého report čte `checksGreen`. Aplikace testy nespouští, jen bere jejich výsledek na vědomí; oprava je nový záznam, nikdy přepis.

OporaHub (`opora_hub.py` + `opora_hub_store.py`) verzuje zadání a práci mimo git: commit patří jednomu rozsahu (oblast, sektor, uzel), má rodiče, jeho `id` je otiskem obsahu a leží v souboru `<projekt>/oporahub/<id>.json`, zatímco tabulka `opora_commits` je jen index, který `rebuild_index` z těch souborů kdykoli postaví znovu; nové snímky z `opora_proposals.py` může navrhovat agent, legacy commit a merge přes HTTP vyžadují session člověka. Historický diff porovnává uložené snímky; minulý obsah starých záznamů bez snímku nevymýšlí.

Dávka plánu (`canvas_plan.py`, cesta `POST /api/canvas-plan`, kontrakt `docs/davka-planu.md` §3) jedním zápisem přidá uzly, vazby, spec, text, bloky s porty, pravidla a rozhodnutí; buď celá, nebo nic. Sestavení v paměti je `canvas_plan_build.py`, poloha nových uzlů `canvas_plan_layout.py` (mřížka pod existujícími, karta celá v oblasti; plná oblast vyroste, dokud jí nestojí v cestě soused), souhrn `canvas_plan_summary.py`. Validují stávající validátory grafu, stavu Desktop v3, specu a textu; graf se zapisuje poslední uvnitř jedné SQLite transakce.

Architektura projektu (`project_architecture.py` + čisté funkce `architecture_graph.py`, kontrakt `docs/domeny-a-worktree.md` §4): domény a stránky (uzly se `site` a jejich předkové) leží jednou pro projekt v tabulkách `project_architecture` a `project_architecture_revisions`, ne v grafu prostoru. `view` vrací architekturu ∪ obsah prostoru (digest ze složeného grafu, navíc `architectureEditable`, `architectureRevision`, `conflicts`), `save_graph` a `apply_plan` složený graf rozdělí a architekturu smí měnit i Git main. Krok zpět a obnova verze vracejí jen obsah; architekturu vrací `POST /api/project-architecture/restore`. Zadání a text uzlu architektury leží pod prostorem `architecture`. Odebrání uzlu architektury se odmítne, když na něj odkazuje obsah jiného prostoru nebo `workspaces.node_id`; smazaná ID se skryjí i ve starých kopiích grafu.

Zápis srdce do architektury (`architecture_order.py`, `docs/navrhy/2026-10-31-poradi-karty.md` §4): `POST /api/project-architecture` s tokenem srdce projde jen při plné autonomii projektu (jinak 403 `heart_architecture_autonomy`) a jen když se proti uložené revizi mění pole `order` existujících uzlů (jinak 422 `heart_architecture_scope`); zápis člověka beze změny.

Migrace architektury (`migrate_architecture.py` + záloha a návrat `migrate_architecture_backup.py`, kontrakt `docs/domeny-a-worktree.md` §5) převede domény a stránky ze starých grafů prostorů (`drafts.graph`, `canvas/workspaces/<wid>/graph.json` nebo převzatý `opora-canvas.json`, `HEAD:opora-canvas.json` jen čtením) do revize 1 architektury. Nic neslučuje: rozdílné kopie, uzel jinde jako obsah, stejný host u různých ID nebo rozdílné zadání/text vrátí `conflicts[]` a projekt se přeskočí. Běží po fázích (backup → architecture → docs → strip → done, stav v `architecture_migrations`), po pádu pokračuje, hotová nic nedělá. Spouští se ručně: `POST /api/project-architecture/migrate` (výchozí `dryRun`) nebo `uv run python -m backend.canvas.migrate_architecture --data <kořen> --project <id> [--apply | --down <záloha> [--force]]`.

Oddělené změny zadání (`opora_changesets.py`, `opora_change_validation.py`) pracují jen s poli zadání existujících karet. Po výslovném počátečním základu vzniká neměnný návrh bez změny Canvasu. `opora_acceptance.py` ověří přijatou hlavu, graf a pracovní i přijaté dokumentové předpoklady a v jedné SQLite transakci zapíše zadání i přijatou revizi. Autoritativní záznamy druhé etapy vlastní `database/repositories/opora_changesets.py`; nejsou součástí souborového legacy úložiště ani jeho obnovitelného indexu. Přijetí není nezávislé review ani ověření implementace. Úplný kontrakt a zbývající etapy: `docs/oporahub.md`.

Vykonávání přijatého zadání: `opora_executions.py` vlastní claim a obnovu autority, `opora_execution_validation.py` zachycení kontextu, `opora_execution_results.py` idempotentní hlášení a `opora_execution_guard.py` trvalou ochranu před legacy zápisem stavu. Sdílená rezervace zůstává v `card_leases`; nová epoch přežívá uvolnění. Výsledek je pouze hlášený důkaz, nikdy automatické dokončení. Kontrakt: `docs/oporahub-executions.md`.

Stav pro agenty: `opora_agent_state.py` skládá jen ke čtení jeden dokument z existujících služeb, `opora_agent_state_rules.py` drží konstanty a pravidla zdraví etap a `opora_agent_state_pulls.py` volitelnou vazbu na modul execution → PR. `opora_agent_state_commands.py` doplní ke každé `ready` akci hotový řádek klienta `command`. Kontrakt: `docs/oporahub-agent-state.md`.

Stopa práce karty (`card_trail_read.py` sběr faktů, `card_trail.py` čistá projekce, `card_trail_judgment.py` příznaky „potřebuje úsudek“, testy vedle; kontrakt `docs/stopa-prace-karty.md`): `GET /api/oporahub/card-trail` složí z běhů exekucí, úkolů brány, událostí, záznamu činnosti, zpráv na vazbách, PR a `dod.missing` jednu odpověď pro kartu; jen čtení, bez modelu, každý text nese `source`. Příznaky srdci zatím nic nepředávají.

Měřák karty a štítek složitosti (`card_gauge.py`, test `test_card_gauge.py`, kontrakt `docs/navrhy/2026-10-30-metriky-a-spoustece.md` §2–3): čisté funkce bez modelu a bez čtení. Agent-state přidá každé zobrazené kartě `gauge` (kroky a %, dod x/7, soubory, druhy kroků, riziko ze souborů podle pravidel review kódu, `fanIn`/`fanOut`, rozpad, pokusy a selhání, stáří aktivního běhu, `costUsd` zatím null) a `gauge.run` (štítek XS–XL z průhledného součtu bodů → úsilí, dělník, poradce podle O10). Počítá se z faktů, které agent-state už načetl (jedna historie běhů, steady pohled grafu, přijaté dokumenty), nic se neukládá. Při chudých podkladech (≤ 1 krok a 0 souborů, `evidence: thin`) se štítek nevydává: `label` „?“, `recommended` null, běh z `card.effort`/`card.model`, jinak výchozí medium · sonnet+opus (`source: default`); bez souborů se riziko hledá v textu karty (název, `purpose`, `acceptance` kroků) podle klíčových slov globů review pravidel, nejvýš `elevated`. Stabilní část `run` (label, effort, model, advisor, handout, humanReview) nese i zadání běhu (`opora_execution_validation.run_profile`, v1 i řídký kontext v2); běžící běh porovnává otisk s `run` ze svého claimu, takže pozdější změna štítku ho neodvolá.

Živý proces (kontrakt `docs/zivy-proces.md`) rozšiřuje outbox `opora_events`: `process_event_validation.py` hlídá tvar `opora.process-event/1`, `process_ingest.py` zapisuje události kanceláře přes `emit_event` (dedupe podle `external_id`) a počítá zdraví zdrojů, `opora_event_process.py` je čisté mapování `kind` → fáze/stav/titulek, `process_activity_bridge.py` přidá jen paměť a starý commit zadání, které outbox sám nevydává, a `process_signal.py` budí SSE proud po každém zápisu.

Hranice návrhu grafu od srdce (`opora_graph_change_plan.heart_scope`, volá ji `backend/api/editor/opora_graph_routes.py`): `updateNodes` jen s polem `memberOf` (příkaz srdce `member`), `updateEdges` vůbec; jinak `HeartEditRefused` = 422 `heart_edit_scope`. Přírůstky a odebrání (`plan`, `unlink`, `prune`) jdou dál (test_opora_graph_change_plan.py).
